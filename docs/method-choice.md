# 读取方法选型

> 决策时间：2026-11-26
> 结论：**用户态读取**（不用内核驱动）

---

## 1. 三个候选方案

| 方法 | 原理 | 风险 | 复杂度 | 迭代成本 |
|---|---|---|---|---|
| **A. 用户态读取** | `OpenProcess` + `ReadProcessMemory` | 低 | 低 | 改一行 Python 即可 |
| **B. 内核驱动** | kdmapper 映射 BYOVD，驱动内读 | 中 | 高 | 重编译 + 重启电脑 + 重映射 |
| **C. 注入 DLL** | 代码放进游戏进程内 | **高** | 中 | 中 |

---

## 2. RF4 的实际情况

关键证据：**`EISEN0516/RF4-DSen` 长期公开用用户态 `ReadProcessMemory`**，
最新版本 V1.08（2026-08）对应游戏版本 `4.0.25029`，一直可用。

```
✅ RF4 没有拦截用户态 RPM
✅ 没有内核级反作弊
✅ 不需要绕任何保护
```

---

## 3. 与 Apex 的关键区别

Apex 那边是**被逼上驱动**的，不是驱动更好。文档记录：

```
MainModule.BaseAddress -> null（句柄被裁）
ReadProcessMemory      -> err=87
```

拆掉 8 个用户态 hook 后仍然崩溃：

```
BugCheck 0x1E  p1=0xC0000006 (IN_PAGE_ERROR)   ← 刚分配的 RW 页
```

根因是**页表级虚拟化（影子地址空间 / 假 DTB）**：

| 现象 | 解释 |
|---|---|
| 分配 RWX → 0xC000000D | 影子层拒绝可执行 |
| 分配成功但写入崩 | 影子层给了假页 |
| `MmCopyVirtualMemory` 拿到假 DTB | 已记录 |
| ntoskrnl 无 inline hook | 拦截在页表层，不在代码层 |

所以 Apex 里用户态**任何**读取路径都经过假页表，读不到真数据，
必须在内核用自己的 `DirectoryTableBase` 构造 PTE。

对比表：

| | Apex | RF4 |
|---|---|---|
| 反作弊 | EAC + Javelin（页表虚拟化 + 句柄裁剪） | 无 |
| `OpenProcess` | 句柄被裁 | 正常 |
| `ReadProcessMemory` | err=87 | 正常 |
| 地址空间 | 影子 DTB | 正常 |
| 必须驱动 | **是**（唯一路径） | **不是**（只是可选） |

---

## 4. 决定：走用户态

### 理由

**① 验证快**
```
游戏装完 → 跑一条命令 → 5 分钟内知道能不能读
```

**② 迭代快（这条最关键）**

坐标字段需要标定（`MyBoid` 有三个 Vector3 候选 `0x78 / 0x84 / 0x90`），
字段语义也要标定（`Rig` 有 30+ 个混淆字段）。

```
用户态：  改一行 Python → 立刻重跑
内核驱动：改常量 → 重编译 .sys → 重启电脑 → 重映射 → 才能测
```

标定工作需要跑几十次，用驱动完全不可行。

**③ 反作弊风险更低**
```
用户态 RPM 不加载任何内核代码
kdmapper 映射未签名驱动本身就有被检测的风险
```

**④ 已有公开先例**
```
RF4-DSen 用同样方法运行一年多，对应到 4.0.25029 这版
```

---

## 5. 切换到驱动的触发条件

出现任意一条才切：

```
1. ReadProcessMemory 返回 0 / 数据明显不对（被拦截）
2. OpenProcess 拿不到句柄
3. 进程列表里出现可疑的内核保护模块
4. 读取触发崩溃或被踢
```

这四条都能在最初 5 分钟内验证出来。

## 6. 备用驱动

`driver/rf4drv.c` 已写好（未编译、未测试），功能完整：

```
· IL2CPP 链路解析全在驱动内完成
· 结果写成紧凑二进制 feed（60fps），用户态只读 feed
· pos 命令可运行时切换坐标偏移（不用重编译）
· probe 命令可直接 dump 候选字段
```

如果用户态走不通，编译映射即可用，不用重写。
